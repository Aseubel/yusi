# LifeGraph 生活关系图与独立来源追踪设计

## 状态

- 设计范围：Diary / 用户本人发布的 Plaza 卡片 / LifeGraph 来源追踪
- 状态：已实现（设计与当前后端实现已对齐）
- 日期：2026-08-13

## 背景

当前 `DiaryChangedEvent` 会创建 LifeGraph 任务，由 GraphRAG 抽取实体、关系和提及。实体提及已经通过 `life_graph_mention.diary_id` 保存来源，但关系来源正在从单一的 `evidence_diary_id` 迁移为独立的来源证据。当前模型还存在三个边界问题：

1. 任何被模型列出的实体都可能直接进入长期图谱，导致标题、普通活动、知识介绍和短暂状态污染 LifeGraph。
2. 关系当前按无向边聚合，不能可靠表达“谁喜欢什么”“用户与谁是什么关系”等方向语义。
3. Plaza 认知事件没有实体来源证据，且认知路由中的 `interests`、卡片情绪标签等结果可能绕过 GraphRAG 直接写入实体。

LifeGraph 的产品定义调整为：

> LifeGraph 是围绕用户本人及其重要人物构建的长期生活记忆图谱，记录用户生活经历、直接生活关系，以及重要人物相关的长期有价值信息。

它服务于两个核心场景：

- 用户回顾自己的生活经历和关系变化；
- Agent 根据用户问题检索长期、可解释、可追溯的生活记忆。

LifeGraph 不是从用户内容中抽取出的全部知识图谱。抽取范围可以很宽，但进入长期图谱的升级标准必须严格。

## 目标

- Diary 和用户本人发布的 Plaza 卡片都能作为有来源的 LifeGraph 输入。
- 输入阶段可以识别 `Person`、`Place`、`Event`、`Work`、`Topic`、`Emotion`、`Item` 等宽范围实体。
- 只有与用户本人或已确认的重要人物存在明确生活语义关系、且有原文证据的实体和关系，才能升级写入长期 LifeGraph。
- 自动写入的拓扑边界是：`User -> 重要人物 -> 人物属性或事件`。
- 这个自动写入边界不限制 LifeGraph 已存在的关系数量，也不限制 GraphRAG 查询时的多跳遍历深度。
- 每个实体和关系贡献都能定位到 `DIARY` 或 `PLAZA` 来源，并可在来源修改、删除时独立撤销。
- 同一来源重复处理是幂等的，不重复增加实体计数、关系权重或证据行。
- 低价值的 `MENTIONED`、`SAID` 等语言事件关系不进入长期 LifeGraph。
- 保留人工创建的实体和关系，并兼容无法完全还原来源的历史数据。

## 非目标

- 不把 Plaza 浏览、共鸣、点赞、收到信号等行为写入用户 LifeGraph。
- 不把用户看到的他人 Plaza 卡片作为用户自己的认知来源。
- 不把所有局部实体持久化来追求“完整图谱”。与用户生活无关的背景知识只在当前抽取上下文中存在。
- 不把人物的同事、朋友及其属性沿图关系自动递归扩展成用户长期人物网络。
- 不把原始日记正文、原始 Plaza 内容或敏感片段暴露给来源接口。
- 不把每次 LLM 原始响应作为用户可见数据长期保存。
- 不新增第二套 LifeGraph 产品页面或第二个图谱模型。

## 核心边界

### 四个不同的范围

必须区分以下四个概念：

| 范围 | 规则 |
| --- | --- |
| 抽取范围 | 宽。可以识别文本中的所有候选实体和局部关系。 |
| 长期升级标准 | 严。必须有用户生活语义、原文证据和允许的关系类型。 |
| 自动写入深度 | 有限。自动升级只从用户扩展到直接重要人物，再扩展到该人物的一跳属性或事件。 |
| GraphRAG 查询深度 | 不限定为一跳或两跳。可按问题进行多跳遍历，但受路径质量和运行预算控制。 |

“最多一跳人物扩展”是自动写入边界，不是查询深度限制。

### 宽抽取与严格升级

抽取阶段允许识别：

```text
Person / Place / Event / Work / Topic / Emotion / Item
```

但抽取结果首先是本次输入的局部上下文，不等于长期实体。服务端必须在写入前执行升级判定，不得因为模型返回了实体、实体置信度较高、实体被多次提及，或实体与已升级实体相连，就自动将其升级。

允许升级的最低条件：

1. 实体或关系在输入中有明确证据片段；
2. 关系有明确语义方向或明确的用户生活参与关系；
3. 关系类型属于长期生活关系白名单；
4. 关系的一端是用户本人，或另一端是已经确认的重要人物；
5. 不属于引用、假设、转述、背景知识介绍、标题总结或普通语言事件；
6. 通过来源类型对应的置信度和重要性门槛。

例如：

```text
我给我女朋友小美买了她最喜欢的草莓蛋糕。
```

可以升级为：

```text
User -> PARTNER_OF -> 小美
小美 -> LIKES -> 草莓
User -> BOUGHT_FOR -> 小美
```

而下面的内容不应仅因出现于正文就升级：

```text
小美说她同事喜欢篮球。
```

这里不能自动创建“小美的同事”作为长期人物，也不能创建该人物的篮球偏好。若该信息没有对用户生活的独立长期价值，整段只作为当前输入的局部上下文。

### 重要人物范围

只有与用户存在直接、明确且有长期价值关系的人物，才进入重要人物层。可接受的入口包括：

- 用户明确声明关系，例如“这是我女朋友小美”“妈妈喜欢兰花”；
- Diary 或 Plaza 中多次形成稳定的用户直接生活关系；
- 用户与该人物存在多个重要事件或持续互动；
- 用户主动将人物标记为重要人物。

人物重要性不是简单的出现次数。被一篇知识介绍反复提到的人物仍然可能与用户无关。自动抽取产生的人物默认是候选，只有直接用户关系通过升级判定后才成为长期重要人物；人工标记可以直接激活，但仍必须留下人工来源或操作审计。

自动升级的拓扑边界为：

```text
User
  -> direct relationship -> Important Person
  -> person attribute/event -> Place / Event / Work / Topic / Emotion / Item
```

自动升级不得继续沿 `Important Person -> Person -> ...` 扩散新人物。人物之间的关系如果未来确有产品价值，可以由用户人工创建或单独设计审核流程，但不属于本次自动写入范围。

## 数据模型

### LifeGraphEntity

现有 `life_graph_entity` 保留用户范围、生命周期和 `origin` 字段，并做以下调整：

- `EntityType` 增加 `Work`，避免把作品和普通 Item 混为一类；
- 增加一等字段 `importance`，范围 `0-1`，表示实体对用户长期生活记忆的价值；
- 继续使用 `last_mention_at` 作为最后一次有证据来源出现的时间，不新增重复的 `last_seen_at` 字段；
- `Person` 的用户关系由指向 `User` 的直接关系决定，`relation_to_user` 可以作为读取投影，但不能成为与关系表不一致的第二事实源；
- `confidence` 表示抽取可信度，`importance` 表示长期价值，两者不能互相替代；
- `mention_count` 应按不同来源贡献聚合，同一来源重复处理不得重复计数；
- 自动生成实体使用 `origin=AUTO`，人工创建或人工确认的实体使用 `origin=MANUAL`；
- `match_allowed`、`hidden`、`valid_until` 继续由生命周期策略控制，Plaza 自动实体默认 `match_allowed=false`。

重要人物的关系角色优先从 `User -> Person` 的关系边推导，例如 `PARTNER_OF`、`FAMILY_OF`、`FRIEND_OF`、`COLLEAGUE_OF`。如果前端需要快速显示“伴侣/家人”等标签，可以将其作为受关系事实驱动的读取投影，而不是让模型任意写入一个无法校验的字符串。

### LifeGraphRelation

长期关系必须保留语义方向。建议保留现有 `source_id` / `target_id` 作为物理图边端点以兼容历史索引，同时增加：

- `semantic_source_id`；
- `semantic_target_id`。

新抽取关系使用语义方向字段表达“谁对谁做了什么”；物理端点继续用于无向邻接和去重兼容。新关系的唯一性应基于 `user_id + semantic_source_id + semantic_target_id + type`，历史只有物理端点的关系标记为遗留来源，不作为新抽取的语义依据。

关系类型分为三组：

1. 用户与重要人物：`PARTNER_OF`、`FAMILY_OF`、`FRIEND_OF`、`COLLEAGUE_OF`、`MENTOR_OF` 等；
2. 用户或重要人物与生活对象/事件：`LIKES`、`DISLIKES`、`BOUGHT_FOR`、`PARTICIPATED_IN`、`EXPERIENCED`、`HAPPENED_AT`、`TRIGGERED` 等；
3. 仅兼容历史或人工使用的通用关系：`RELATED_TO` 等。

`MENTIONED`、`MENTIONED_IN`、`SAID` 以及同类只描述语言出现过程、没有独立长期检索价值的关系，不进入自动长期 LifeGraph。它们可以留在本次抽取结果中供判断使用，但不写入关系聚合表。

### 通用实体来源证据

当前 `life_graph_mention.diary_id` 只支持日记来源，不能承担 Plaza 的独立撤销。推荐新增通用 `life_graph_entity_evidence`，并逐步让实体来源 API 统一从该表读取：

| 字段 | 作用 |
| --- | --- |
| `user_id` | 所属用户，所有查询和删除必须带上 |
| `entity_id` | 被来源贡献的实体 |
| `source_type` | `DIARY`、`PLAZA`、`MANUAL`、`LEGACY` 等 |
| `source_id` | 日记业务 ID 或 Plaza card ID |
| `occurrence_count` | 该来源的有效贡献次数 |
| `evidence_kind` | 用户关系、人物属性、事件参与等证据类别 |
| `snippet` | 脱敏后的短证据片段，可为空 |
| `entry_date` / `source_time` | 来源时间元数据 |
| `props` | 偏移、局部抽取标识等扩展数据 |
| `created_at` / `updated_at` | 审计时间 |

唯一键至少为 `user_id + entity_id + source_type + source_id`。同一来源对同一实体重复处理时更新原行，不新增贡献。

现有 `life_graph_mention` 保留兼容 Diary 读取和历史数据；新代码应避免再把 `diary_id` 作为所有实体来源的唯一模型。Memory Center 的安全来源接口需要同时支持 Diary 和 Plaza，并根据来源类型返回安全标题或业务跳转信息，不能返回原始正文。

### 关系来源证据

继续使用 `life_graph_relation_evidence` 保存关系贡献：

| 字段 | 作用 |
| --- | --- |
| `relation_id` | 聚合关系 ID |
| `source_type` | `DIARY` 或 `PLAZA`；历史未知贡献使用 `LEGACY` |
| `source_id` | 日记 ID 或 Plaza card ID |
| `occurrence_count` | 该来源对关系权重的贡献 |
| `evidence_snippet` | 脱敏后的关系证据 |
| `confidence` | 来源证据置信度 |

唯一键为 `user_id + relation_id + source_type + source_id`。`life_graph_relation.weight` 是来源证据汇总结果；`manual_weight` 是人工基线，来源撤销不能删除人工基线。

## Diary / Plaza 抽取与升级流程

### 两阶段处理

Diary 和用户本人发布的 Plaza 卡片采用相同的逻辑边界：

1. **宽抽取阶段**：识别所有局部实体、候选关系、证据片段和时间信息；结果只作为当前处理上下文。
2. **严格升级阶段**：结合用户节点、已确认的重要人物、关系白名单、来源类型、置信度和重要性，决定哪些结果写入长期 LifeGraph。
3. **服务端硬校验**：拒绝非法实体类型、缺失证据、非白名单关系、人物递归扩散和不能解析到已升级节点的关系。
4. **来源化写入**：只对通过升级的实体和关系写入实体证据、关系证据、聚合节点和别名。

实现可以使用一次结构化模型调用同时返回 `local` 和 `upgraded` 两组结果，也可以使用“宽抽取 + 独立升级判断”两次调用。无论使用哪种方式，最终写入必须经过服务端规则校验，不能完全信任模型的升级标记。

### Plaza 来源边界

- 只有卡片作者本人可以成为 `user_id` 的认知来源；当前卡片必须通过 `card.user_id == command.userId` 校验。
- Plaza 来源统一使用 `source_type=PLAZA`、`source_id=cardId`；不能使用可能指向日记或情景室的 `originId`。
- 新发布、修改和删除分别对应来源创建、来源替换和来源撤销。
- 卡片的分类情绪标签只用于 Plaza 展示和局部输入上下文，不能直接创建用户 `Emotion` 实体。
- Plaza 的公开表达权重低于 Diary；默认不允许自动实体参与匹配。只有用户后续明确调整生命周期，才可以改变使用范围。
- Plaza 中背景知识、引用、转述和与用户生活无关的实体不进入长期 LifeGraph，也不为了完整性新增局部实体表。

### 人物升级规则

直接用户关系是重要人物进入长期图谱的必要入口。处理顺序应为：

1. 先判定 `User -> Person` 的直接关系是否明确、重要且有证据；
2. 通过后激活或更新该人物的 `Person` 实体及关系来源证据；
3. 再只处理该人物在同一来源中有独立证据的一跳属性或事件；
4. 对 `Person -> Person` 的新人物扩展默认拒绝；
5. 删除或修改来源时，人物及其属性关系只撤销该来源的贡献，其他 Diary/Plaza 来源继续保留。

一条来源中同时出现“用户关系”和“人物属性”时，可以在同一事务中先写入人物关系，再写入人物属性关系。例如“我女朋友小美喜欢草莓”允许写入 `PARTNER_OF` 和 `LIKES`；但“某篇文章介绍小美的同事喜欢篮球”没有用户直接关系，不触发人物升级。

### 低价值关系过滤

以下关系仅用于局部判断，不写入长期关系表：

- 只说明“文本提到了某人”的 `MENTIONED` / `MENTIONED_IN`；
- 只说明“某人说了某句话”的 `SAID`；
- 没有具体生活语义的泛化 `RELATED_TO`；
- 标题与正文相同的总结关系；
- 单次无长期价值的普通动作或临时状态。

## 来源撤销与重建设计

### Diary 修改、删除和重试

以 `user_id + diary_id` 合并待处理任务，保证同一来源不会并发重建。处理时：

1. 读取当前 Diary 版本并完成宽抽取和严格升级；
2. 在来源替换事务中删除该 Diary 的实体证据和关系证据；
3. 按剩余来源重新汇总实体计数、关系权重和 `evidence_diary_id` 兼容字段；
4. 写入新版本通过升级的实体、实体证据、关系和关系证据；
5. 没有剩余来源的自动实体及其别名删除；没有剩余自动证据的自动关系删除；人工基线保留；
6. 同一来源写入使用唯一键或等价幂等逻辑；
7. 抽取失败时任务保持可重试状态，不标记成功。

如果 Diary 被删除、为空或无法解密，只执行来源撤销，不生成新结果。来源撤销必须按 `user_id` 限制，不能跨用户影响同 ID 数据。

### Plaza 修改、删除和重试

Plaza 卡片的来源生命周期与 Diary 相同，但来源键为 `PLAZA + cardId`：

1. 新卡片保存成功后异步执行一次宽抽取和严格升级；
2. 修改卡片时重新分析当前内容，成功进入替换事务后撤销旧 Plaza 来源并写入新结果；
3. 删除卡片时撤销该卡片的实体证据和关系证据，不影响其他来源；
4. 卡片不存在、内容为空或脱敏后为空时，只撤销旧来源；
5. 重试和重复事件不能增加来源贡献。

Plaza 的中期记忆可以继续按 `source_type=EMOTION_PLAZA` 独立管理，但不能以认知路由中的 `interests` 或 `topic` 绕过 LifeGraph 升级流程直接创建长期实体。

## GraphRAG 查询与路径质量

### 查询深度

GraphRAG 查询不受自动写入“一跳人物扩展”限制。用户询问复杂生活关系时，可以遍历多跳关系，包含：

```text
User -> Important Person -> Event -> Place -> Topic
```

系统只设置运行时预算，如最大节点数、关系数、路径数、模型上下文长度和超时，不设置“最多一跳/两跳”的产品硬限制。遍历必须使用 visited 集合避免环路。

### 路径质量约束

多跳结果按以下因素过滤和排序：

- 关系类型是否具有长期生活语义，低价值语言事件不参与路径；
- 每条边是否有来源证据；自动关系优先要求 `DIARY` / `PLAZA` 证据；
- 来源是否对当前用户可见、未隐藏、未过期且属于当前用户；
- 关系和证据的 `confidence` 是否达到查询场景门槛；
- 多条路径是否有来源独立性和时间一致性；
- 路径是否包含用户节点或已确认的重要人物，避免从孤立局部实体漫游；
- 结果是否与查询实体和时间范围匹配。

查询结果应返回实体、方向关系、置信度、来源类型和安全来源 ID。Agent 可以据此回答，但不能把查询过程中新推断出的关系反写为长期事实。

## Timeline 与用户回顾

LifeGraph 仍是 Timeline 的底层数据来源之一，但进入 LifeGraph 不等于自动生成 Timeline 节点：

- 只有 `Event` 且具有明确时间或来源日期的实体才具备 Timeline 候选资格；
- 人物喜好、关系标签和普通 Topic 不生成 Timeline 节点；
- Plaza 来源的个人事件只有在有明确用户参与关系、时间证据和足够重要性时才可作为 Timeline 候选，权重低于 Diary；
- 删除或修改来源后，Timeline 只保留仍有有效来源贡献的事件；
- Timeline 展示使用安全标题和来源跳转，不暴露原始敏感片段。

这样可以同时支持“回顾我和小美第一次旅行去了京都”和“查询小美喜欢什么”，但不会把每个被提及的人或普通情绪变成时间线节点。

## Memory Center 与 Agent 读取

Memory Center 展示的是长期派生认知的控制面，不是原文阅读器：

- 人物显示其关系角色、重要性、置信度、生命周期和安全来源；
- 关系来源支持 `DIARY`、`PLAZA` 等类型；
- Diary 来源显示标题并可跳转详情；Plaza 来源显示安全的卡片标识或卡片入口，不返回正文片段；
- 用户隐藏、过期或删除一个实体时，Agent、匹配、Timeline 和图查询都使用一致的可见性过滤；
- `match_allowed=false` 只影响匹配，不阻止用户回顾或 Agent 在可见范围内检索；
- 用户删除自动实体时，同时撤销其来源证据、别名、关系和合并记录，但不删除原始 Diary 或 Plaza 卡片。

Agent 的 LifeGraph 工具应优先返回“用户—重要人物—生活属性/事件”的关系上下文，而不是孤立实体列表。来源证据用于解释和置信度控制，不得把原始敏感文本直接拼进工具结果。

## 一致性与失败处理

- 来源撤销、聚合计数更新、证据写入在同一数据库事务内完成。
- LLM 调用和多跳查询不在持有数据库锁的长事务中执行。
- 新写入必须先通过 JSON、实体类型、关系类型、证据存在性和升级拓扑校验。
- 模型返回非法类型时直接丢弃，不再静默降级为 `Topic`。
- 模型没有返回 `mentions` 时，只能对已经通过严格升级的实体使用其明确关系证据或受控来源证据，不能无条件把所有抽取实体补成来源。
- 关系来源和实体来源都必须包含 `user_id + source_type + source_id` 约束，禁止跨用户撤销。
- 处理失败时任务可重试；重复任务必须幂等；不能因为重试而累加权重。
- 历史无法还原的实体和关系不在本次范围内清理；通过 `LEGACY` 或现有兼容字段隔离，避免影响后续来源撤销。

   - 明确重要人物及其一跳属性/事件边界、关系方向、证据要求和多跳查询不受自动升级边界限制。

对应实现职责：

- `LifeGraphPromotionPolicy` 在服务端再次校验实体类型、关系类型、证据片段、关系置信度和自动升级拓扑；模型返回的候选实体不会直接成为长期事实。
- `LifeGraphBuildServiceImpl` 对 Diary / Plaza 使用来源替换写入；实体证据、关系证据、聚合计数和来源撤销按用户与来源键隔离，并保持幂等。
- `PlazaLifeGraphListener` 只处理用户本人发布的 Plaza 来源；Plaza 的展示标签不会绕过升级策略直接创建长期实体。
- `LifeGraphQueryService` 支持超过一跳的 GraphRAG 查询，并按关系类型、来源证据、置信度、可见性和运行预算控制路径质量；“最多一跳”仅属于自动升级边界。
- `LifeGraphLifecycleService` 和来源读取逻辑返回安全的来源元数据：Diary 显示标题并支持详情跳转，Plaza 只显示安全卡片标识，不返回原始正文。

本次实现不包含历史旧实体、旧关系和无法还原来源数据的清理。旧数据通过现有兼容字段或 `LEGACY` 语义保留，后续新增或重建来源必须遵守本设计的证据与升级规则。

## 验证标准

### 抽取和升级

- 输入中可以识别背景人物、作品、地点和知识实体，但无用户生活关系的实体不会进入长期表。
- “我女朋友小美喜欢草莓”可以写入用户—小美关系和小美—草莓属性关系。
- “小美的同事喜欢篮球”不会自动创建小美的同事及其属性。
- `MENTIONED`、`MENTIONED_IN`、`SAID` 和无语义 `RELATED_TO` 不产生自动关系行。
- 非法实体类型不会降级为 `Topic`。
- Plaza 卡片情绪标签不会单独创建长期 Emotion 实体。

### 来源和重建

- 同一 Diary 或 Plaza 来源重复处理两次，实体计数、关系权重、来源行数量不增加。
- 删除或修改一个来源，只撤销该来源贡献；其他 Diary/Plaza 来源保持有效。
- 只有一个来源的自动实体和关系在来源删除后消失；人工实体、人工关系和 `LEGACY` 贡献保留。
- 关系来源支持同一关系同时拥有 Diary 和 Plaza 证据。
- 多用户同一来源 ID 场景不会互相影响。

### 查询和回顾

- LifeGraph 查询可以返回 User 节点和重要人物的方向关系。
- 查询支持超过一跳的路径，并按关系类型、来源、置信度、可见性和运行预算筛选。
- 查询不会把新推断关系反写入数据库。
- 只有有时间证据且重要的 Event 才进入 Timeline；人物喜好和普通 Topic 不生成 Timeline 节点。
- Memory Center 能显示 Diary 标题跳转和 Plaza 安全来源，不泄露原始正文。
