# Yusi Agent 产品与工程演进计划

> **Status:** In Progress — backend foundation first
> **Date:** 2026-08-04
> **Last Updated:** 2026-08-16
> **Scope:** Yusi 的长期记忆 companion、认知、匹配与 Agent 能力演进

## 目标

围绕 Yusi 的核心价值，建立一条从“用户表达”到“被理解”、再到“高质量连接”的可持续闭环。这个闭环允许自然积累，不以快速激活或强行留存为目标：

```text
日记 / 对话 / 广场
        -> 认知与记忆
        -> 洞察、回顾与陪伴
        -> 灵魂匹配
        -> 匿名互动与连接反馈
        -> 改善下一次理解与匹配
```

本计划参考企业 Agent 路线图中的 Agent Runtime、工具治理、评测和反馈闭环，但不复制企业协作助手的渠道、多租户和 Agent Swarm 方案。

当前推进原则：先完善后端系统，再扩展用户可见功能。优先补齐数据正确性、来源追踪、
事件关联、任务幂等与恢复、可观测性、安全审计和可执行评测；主动陪伴、连接触达和
其他产品体验只维护已有行为，新的功能扩展放到后端质量门槛之后。

## 当前基础

Yusi 已具备以下基础能力：

- 日记、AI 对话和灵魂广场进入统一认知编排。
- `lifeGraph`、`user-persona`、`mid-memory` 形成分层认知结构。
- 匹配画像由认知层聚合，并通过 Dense + Sparse + RRF 召回和 LLM 精排生成匹配结果。
- Agent 已支持人格、主动问候、周期性回顾、反馈和多模态输入。
- 本地工具、MCP 工具、模型路由和外部 MCP 网关已经存在。
- 情景室可以独立完成多人情景、提交和 AI 报告生成。

当前的主要问题不是缺少更多基础设施，而是：

1. LifeGraph 的独立来源、严格升级和撤销边界已经落地，但还需要通过统一事件、任务
   重建和评测闭环验证长期运行的一致性。
2. Phase 2 已建立产品事件、任务执行、来源版本和安全审计基础，但推荐生成、AgentRun
   以及模型调用仍需要沿这些边界继续串联。
3. AI 运行过程、认知任务和模型调用缺少统一的 Trace、失败恢复和幂等视图。
4. 记忆抽取、GraphRAG、Timeline、匹配和主动性缺少可重复的离线评测与回归门槛。
5. 主动问候当前仍主要依赖 `mid-memory` 更新时间判断不活跃，活动事件基础未统一；
   这项用户可见功能暂不扩展，待后端活动与质量基础完成后再推进。

### 2026-08-04：完成 AgentRun 对话流可视化

本次实现将用户从发送消息到最终回答的这一条 `/api/ai/chat/stream` 请求视为
一次 `AgentRun`。现阶段复用前端生成的 `requestId` 作为 `runId`，不把单次模型调用、
单个工具调用或 MCP 调用拆成新的 AgentRun：

```text
一次用户任务
  -> 一个 AgentRun（runId = requestId）
      -> 模型调用
      -> 记忆检索
      -> 本地 ToolCall / MCP ToolCall
      -> 最终回答
```

已完成的交付物：

- [x] 后端通过命名 SSE 事件发送 `run.started`、`run.stage`、`tool.started`、
      `tool.completed`、`response.delta`、`run.completed` 和 `run.failed`。
- [x] 阶段覆盖准备、思考、记忆检索、工具调用、回答生成、完成和失败。
- [x] 工具事件只包含调用 ID、工具名、来源、成功状态和耗时；不发送原始思考、
      工具参数或工具结果正文。
- [x] 前端在助手消息中展示 AgentRun 活动面板，并支持工具活动展开/收起。
- [x] 本地工具与 MCP 工具使用不同来源标识；当前 `web_search` 显示为 MCP。
- [x] 普通回答、工具完成、工具失败、连接异常和用户主动停止均有明确的显示状态。
- [x] 保留旧版纯文本 SSE 的解析兼容性。
- [x] 增加工具生命周期事件测试，验证 MCP 工具失败、耗时和敏感内容不外泄。
- [x] 将 `frontend/rebuild.sh` 对齐根目录部署脚本：支持严格失败、可选环境文件、无缓存构建，
      并只回收当前前端镜像，不清理全局 Docker 资源。

前端显示契约如下：

| 情况 | 用户看到的内容 |
| --- | --- |
| 普通回答进行中 | “正在整理问题”或“正在组织回答” |
| 记忆或人生图谱检索 | 友好的检索阶段文案 |
| 本地工具调用 | 工具友好名称、进行中/完成/失败、耗时 |
| MCP 工具调用 | 工具友好名称、`MCP` 来源标识、状态和耗时 |
| 普通回答完成 | 隐藏活动面板，只保留回答正文 |
| 使用工具后完成 | 保留可收起的工具活动记录和工具数量 |
| 工具或模型失败 | 保留失败状态和已生成的回答内容 |
| 用户主动停止 | 显示“已停止”，保留停止前已经生成的内容 |

本次没有提前实现的内容：

- AgentRun 事件目前是流式用户界面事件，还不是持久化 Trace。
- 尚未记录 Prompt 版本、模型调用 Token、费用、完整工具 Schema、重试和幂等信息。
- MCP 仍然只是 AgentRun 内的一种 ToolCall；外部 AI 调用 Yusi MCP 时，完整
  AgentRun 仍属于外部 AI，Yusi 侧只记录一次 MCP invocation。
- 情景室仍是独立小游戏，不自动进入本次 AgentRun 的长期画像或匹配画像。

验证结果：

- 后端 `AiControllerCancellationTest`、`ChatStreamCancellationRegistryTest`：9 个测试通过。
- 前端 TypeScript 检查、Vitest：4 个测试通过。
- 前端 Vite 生产构建通过。
- 本地开发服务可通过 `http://localhost:5174/` 访问。

### 2026-08-04：完成记忆透明度与生命周期切片

本次完成 Phase 1 的 `MidTermMemory`、`UserPersona` 和现有 `LifeGraph` 关系图谱实体

和匹配使用范围，并执行纠正、有效期调整、隐藏/恢复、删除和匹配授权。

实现记录见：[记忆透明度与生命周期](../records/2026-08-04-yusi-memory-transparency-lifecycle.md)。

本阶段的产品边界、工程设计和实现计划见：[记忆透明度与生命周期 PRD](../../prd/2026-08-04-memory-transparency-lifecycle.md)、
[工程设计](../../superpowers/specs/2026-08-04-memory-transparency-long-term-design.md)和
[实现计划](../../superpowers/plans/2026-08-04-long-term-memory-transparency.md)。

- 新生成的中期记忆默认 `matchAllowed=false`，用户显式开启后才参与匹配画像；历史数据迁移保留原有匹配行为。
- 隐藏、过期、已合并和未授权的记忆不进入匹配画像；隐藏和过期记忆也不进入聊天上下文、主动问候和记忆检索。
- 新生成的 Persona 和关系图谱实体默认不参与匹配；隐藏或过期数据从 Agent、洞察、图谱和匹配读取路径排除。
- 记忆中心、关系图谱搜索和 Agent 图谱工具只展示安全摘要和低敏元数据，不返回原始日记、完整对话或 mention 原文片段。
- `/community` 是唯一关系图谱前端入口；`/lifegraph` 已移除且不做兼容重定向。
- 记忆中心统一承接中期记忆、稳定画像和关系图谱生命周期控制，但不新增统一洞察 Hub。
- 修改摘要、匹配授权、隐藏状态或有效期后，必要时刷新匹配画像；向量副本同步失败不会阻断数据库生命周期操作。
- 日记编辑不强制回收全部历史派生记忆，用户通过记忆中心自行微调，避免把日记存储与派生认知强耦合。

### 2026-08-05：完成匹配到连接的第一版生命周期闭环

本次完成连接生命周期第一版，保留 `SoulMatch` 作为一次推荐记录，并新增独立的
`SoulConnection` 作为接受推荐后的连接生命周期记录。一个 `matchId` 当前最多对应一个
`connectionId`，避免把推荐、聊天和连接结果混成同一条记录。

- 接受、拒绝、等待回复、开始互动、双向共鸣、结束、举报和拉黑均有明确状态；双方都提交
  `DEEP_INTERACTION` 后才进入 `MUTUAL_RESONANCE`。
- 匹配响应返回 `connectionId` 和 `connectionStatus`；连接反馈、结束、举报和拉黑接口均按
  `matchId` 定位连接并记录独立 `connectionId`。
- 只有 `STARTED` 或 `MUTUAL_RESONANCE` 连接允许发送聊天消息；`REPORTED` 暂停普通互动，
  `DECLINED`、`ENDED` 和 `BLOCKED` 不允许静默恢复。
- `LIKE`、`DEEP_INTERACTION`、`DO_NOT_CONTINUE`、举报和拉黑作为不同反馈信号记录，强负面
  信号进入后续匹配排除逻辑。
- 数据库迁移为已有已接受匹配回填连接记录和 `match_feedback.connection_id`；旧的已匹配聊天
  在缺少迁移连接记录时保留兼容读取兜底。
- 匹配页已提供轻量连接反馈、结束、举报和拉黑入口；破冰话题与情景推荐仍是可跳过的辅助引导。

本次仍未完成连接产品事件 ID 的统一落库、消息行上的独立 `connectionId`/`runId`，以及完整的
通知和安全审计事件链；这些属于 Phase 2 后续工作。

### 2026-08-14：完成 Phase 2 后端基础设施

Phase 2 的五个后端切片已完成并分别提交：产品记录跨流程关联、产品事件幂等账本、任务执行
账本、来源版本与派生数据幂等，以及安全审计轨迹。它们保持业务表为事实来源，不引入通用
事件溯源平台；产品事件、任务执行和安全审计分别承担业务事实、后台状态和安全追责职责。

- 连接、通知、聊天和匹配结果可以沿 `matchId`、`connectionId`、`runId` 和事件 ID 关联。
- Diary / Plaza 派生任务以用户、来源、来源版本和任务类型组成幂等边界，旧版本结果不能覆盖新版本。
- 任务失败、重试耗尽和恢复状态进入任务执行账本，审计只保存低敏动作、主体、资源、结果和分类 metadata。
- 安全审计按用户/参与者 scope 查询，管理员查询需要显式授权，过期记录先删除 scope 再删除事件。
- 后续 Phase 3 可以直接复用这些关联和安全边界扩展 AgentRun、模型、Prompt、记忆检索和工具 Trace，
  但不把用户可见功能提前到基础设施尚未验证之前。

### 2026-08-16：完成聊天工具 Trace 与依赖兼容刷新

本次完成 Phase 3 的聊天工具调用低敏 Trace 切片。工具调用作为 `AgentRun` 的持久化子记录，
保存本地生成的稳定 `toolCallId`、工具名称、来源、生命周期、耗时和固定失败分类；不保存查询、
参数、召回正文、工具结果、Prompt、模型输出、思考内容或密钥。

- `beforeToolExecution` 始终由后端生成本地唯一 ID；LangChain4j/MCP 的上游请求 ID 只作为可空的
  `upstreamToolCallId` 参考字段，不能承担幂等键职责。SSE 的开始和完成事件使用本地 ID。
- 工具调用通过请求对象 identity、上游 ID 和同名工具 FIFO 兜底关联；AgentRun 的 complete、fail、
  cancel 三个终态统一收敛同一运行下仍为 `RUNNING` 的工具 Trace，避免取消路径留下孤儿记录。
- `agent_run_trace.tool_count` 语义保持不变，仍表示已完成工具调用总数；`failureCategory` 只按固定
  枚举和 `hasFailed`/异常类型分类，不从工具结果文本或异常 message 推导原因。
- 本切片不覆盖 `McpGrpcServiceImpl` 中原始 `keyword/query` 日志，另立日志安全切片处理。
- Hutool 从 `5.8.24` 刷新到已核对的 `5.8.39`；Spring、LangChain4j、gRPC 等高耦合依赖保持不变。

本次没有提前扩展新的用户流程。工具能力 Schema/权限治理、取消传播、暂停恢复以及固定样例评测
仍属于 Phase 3/4 后续工作。

### 2026-08-16：完成 Agent 最终响应低敏摘要

本次完成聊天 AgentRun 的最终响应元数据切片。`agent_run_trace` 现在保存助手流式响应中已接收的
Unicode code point 数量；正常完成、模型失败和用户取消都会沿同一终态写入，因此失败或取消前
已经生成的部分回答也能被识别。数据库仍不保存响应正文、用户查询、Token 内容、Prompt 或工具结果。

- 响应数量只在聊天进程内从非空 `PartialResponse.text()` 累加，最终以 `response_char_count` 写入；
  它不是 Token 数、grapheme 数或可还原正文的字段。
- `AgentRunTraceService` 保留原有后台任务接口，非聊天运行默认记录 `0`；负数输入归零，终态更新
  继续幂等，不改变 `tool_count` 的“已完成工具调用总数”语义。
- `searchMemories`、`searchDiary` 和 `searchLifeGraph` 继续由 `AgentToolTrace` 记录调用生命周期，
  不新增内部检索明细表；记忆检索算法和 GraphRAG 查询深度不在本切片内调整。

### 2026-08-16：完成工具能力契约切片

本次补齐 Phase 3 的第一层工具治理边界：本地工具从实际 `@Tool` 定义生成参数 Schema，MCP 工具

- `agent_tool_trace.capability_version` 记录一次实际调用使用的能力契约版本，使 run 回放可以解释

- `agent_run_trace.tool_count` 语义保持不变，仍表示已完成工具调用总数；本切片不引入超时、重试、
  幂等键或取消传播策略。

### 2026-08-16：完成工具执行超时与取消传播切片

本次在本地工具和 MCP 工具之间建立统一的执行策略边界：工具调用在专用线程池中执行，按能力
类型施加超时，并从聊天流 session 将用户取消传播到正在运行的工具。超时和取消只做一次终止尝试，
底层客户端是否响应线程中断仍由其自身实现决定；本切片不假设可以强制停止已经产生副作用的外部调用。

- `AgentToolExecutionPolicyService` 同时包装 `@Tool` 本地 executor 和动态 MCP `ToolProvider` 返回的
  executor，策略由工具能力目录统一提供；当前 memory read、persona write、MCP network read 和未知
  工具分别使用固定超时，线程池大小由 `agent.tool.execution.pool-size` 配置。
- `ChatStreamSession` 持有 `AgentCancellationToken`，取消或失败时先标记令牌，再取消流句柄；
  `ModelRouteContext` 和 `ModelRouteContextHolder.getEffective()` 将令牌传递到工具执行线程，避免
  session 从 registry 移除后丢失取消信号。
- 超时抛出固定的 `AgentToolTimeoutException`，取消抛出固定的 `AgentToolCancelledException`；
  不从异常 message 或工具结果推导失败类别，也不在本切片引入自动重试、幂等键或用户确认。
- `agent_run_trace.tool_count` 语义保持不变，仍表示已完成工具调用总数；`McpGrpcServiceImpl` 的
  原始 `keyword/query` 日志收敛仍属于独立安全日志切片。

本次没有提前扩展新的用户流程。工具重试、工具幂等键、写操作确认、暂停/恢复和固定样例评测仍属于
Phase 3/4 后续工作。

### 2026-08-16：完成工具超时重试与尝试计数切片

本次在统一工具执行包装层补充受能力契约约束的超时重试。抽取范围仍然保持宽，但能力目录只有明确
声明为 `READ/TIMEOUT_ONCE` 的只读工具允许一次超时重试；写操作、未知能力以及普通工具失败均不自动
重试。重试不扩展到 Controller、具体工具或 MCP 服务内部。

- 每次逻辑工具调用最多两次物理尝试，所有尝试共享不超过 30 秒的总 deadline，显著低于聊天 SSE 的
  180 秒生命周期；只有固定的 `AgentToolTimeoutException` 触发重试，`TOOL_FAILED`、`CANCELLED`、
  `UNKNOWN` 不重试。
- 重试退避使用可唤醒的取消令牌，等待期间收到取消会立即结束逻辑调用，不发起下一次尝试；
  取消或完成/失败/取消任一 run 终态都会清理未完成的请求身份注册。
- 专用线程池默认 8 个 daemon worker、16 个有限排队槽位，使用 `AbortPolicy`，不回退到调用线程。
  超时后不响应中断的旧尝试可能继续占用一个 worker，一次重试窗口最多同时占用旧尝试与新尝试两个
  槽位；本次不自动扩大池容量，也不创建第二个重试池。
- `agent_tool_trace.attempt_count` 只记录物理尝试数量，范围为 1 或 2，不保存参数、结果、Prompt、
  用户 query 或异常文本；`agent_run_trace.tool_count` 仍表示完成的逻辑工具调用数量，不按重试次数增加。
- 本次仍不实现通用幂等键、写操作用户确认、跨请求恢复，也不覆盖 `McpGrpcServiceImpl` 中原始
  `keyword/query` 日志收敛；失败分类继续只依据异常类型或 `hasFailed`。

### 2026-08-16：完成声明式写工具幂等账本与重复执行保护

本次完成 Phase 3 的声明式写工具保护切片。幂等账本复用 `agent_tool_trace`，不新增独立的
`idempotency_key`：Controller 生成的 `localToolCallId` 同时作为 `tool_call_id`、SSE 工具事件 ID、
Invocation Context 中的调用 ID 和账本 key。只有能力目录明确声明为 `WRITE + IDEMPOTENT_WRITE` 的工具
才进入账本；当前真实消费方只有本地 `updateUserPersona`，默认能力和未知工具仍拒绝自动重试及幂等写入。

- `updateUserPersona` 首次执行先原子 claim，Context 在专用 worker 中传播用户 ID 并被真实工具消费；同一
  本地调用 ID 的重放返回 `isError=true` 的稳定阻断响应，业务画像服务不会再次执行。
- 写工具没有自动超时重试；超时、取消、线程池提交失败和 run 终态收敛会把 `CLAIMED` 账本置为
  `UNKNOWN`，`UNKNOWN`、`COMPLETED`、`FAILED` 和并发 claim 失败都不会静默调用 delegate。启动扫描将
  超过 5 分钟的孤儿 `CLAIMED` 置为 `UNKNOWN`，账本状态保留 30 天。
- `AgentToolInvocationContext` 的显式跨线程传播已通过技术验证，不启用隐式 ThreadLocal 继承，也不需要
  `ModelRouteContextHolder` 退回方案。`agent_run_trace.tool_count` 仍表示完成的逻辑工具调用总数，不按
  claim 或物理尝试次数增加。
- 本次不覆盖 `McpGrpcServiceImpl` 中原始 `keyword/query` 日志，不增加用户确认、暂停/恢复或跨请求重放；
  这些边界另行切片处理。

## 设计决策

### 1. 产品优先于平台扩张

Yusi 的核心产品是“隐私优先的长期记忆 AI companion”，不是通用企业办公助手。后续优先提高理解质量、陪伴质量、连接质量和用户信任，不优先建设企业 IM 适配、多租户计费或工具市场。

### 2. 接受自然数据积累

用户没有足够日记、对话或互动数据时，Agent 无法形成深度理解是正常状态。项目不通过强制 onboarding、奖励机制、连续打卡或留存指标人为填充数据。

早期数据少时，系统可以保持克制：提供有限的当前上下文理解，不伪造稳定画像，也不为了让用户留下而过度主动打扰。产品质量主要看已有数据被使用得是否准确、透明和安全，而不是新用户是否被快速转化或长期留存。

### 3. 保持一个 Yusi Agent，按能力扩展

现阶段采用“一个主 Agent + 认知、记忆、匹配、报告等领域能力”的结构。只有当任务出现明确的多步骤协作需求时，才引入 Supervisor 或专业 Agent，不为了架构形式强行拆分多个 Agent。

### 4. Agentic 只用于长流程和确认流程

普通聊天、认知摄取、匹配画像刷新和周报生成继续由现有 Spring Service 和异步任务承载。需要计划、等待、用户确认、恢复或补偿的流程，再引入持久化 Agent Run，例如：

- 用户请求删除一组长期记忆。
- Agent 整理一段较长的人生阶段记录。
- 用户确认后才把一次情景结果用于匹配。

### 5. 先做评测，再考虑训练

当前不建设完整的微调或训练工厂。先收集可复现的对话、记忆和匹配评测样例，建立 Prompt、模型和检索策略的回放比较能力。没有可靠评测之前，训练不会自动带来可靠提升。

## 范围与非目标

### 本计划范围

- 记忆的透明度、权限和生命周期。
- 匹配后的连接闭环和安全反馈。
- 主动陪伴的触发质量和用户控制。
- Agent Run、工具调用和模型调用的可观测性。
- 对话、记忆、匹配和主动性的离线评测。
- 长流程 Agentic 能力的最小公共基础。

### 暂不作为主线

- 新用户冷启动、激活漏斗和留存优化。
- 强制 onboarding、连续打卡或奖励式数据收集。
- 飞书、Slack、钉钉等企业渠道适配。
- 企业多租户、组织权限、计费和配额平台。
- 完整的四专家 Agent Swarm。
- MCP 工具市场和第三方工具生态。
- 立即建设模型微调和训练工厂。
- 将情景室自动写入长期画像或自动影响所有匹配。

- 普通聊天仍保持现有流式体验，不被复杂任务编排拖慢。

### Phase 4：评测、回放与质量回归

**目标：** 在扩展用户可见功能前，建立可重复的质量证据和回归门槛，让 Prompt、模型、
抽取策略和检索策略的变化可比较。

- [ ] 建立对话评测集：记忆引用正确性、语气一致性、幻觉、隐私边界和工具使用边界。
- [ ] 建立记忆评测集：实体/关系抽取、LifeGraph 升级、来源撤销、去重、冲突识别、
      有效期和删除生效。
- [ ] 建立 Timeline 评测集：事件资格、时间证据、来源安全性和修改/删除后的重建结果。
- [ ] 建立匹配评测集：召回覆盖、精排理由、双向共鸣、接受率、持续互动和强负面排除。
- [ ] 建立主动性评测集：触发是否合理、活动判断是否准确、内容是否重复、是否造成打扰。
- [ ] 支持固定样例回放和 Prompt/模型/检索版本对比，记录输入版本、输出摘要和评测结果。
- [ ] 将用户反馈转成脱敏、可标注的数据，不直接把所有反馈写回画像或训练数据。
- [ ] 为关键指标设置回归门槛，任何质量提升都不能以隐私、安全、删除生效或来源正确性
      下降为代价。

**验收标准：**

- 修改模型、Prompt、升级策略或检索策略后，可以与基线进行固定样例对比。
- LifeGraph、Timeline、记忆删除和安全边界有自动化回归结果，而不是只依赖线上观察。
- 匹配和主动性调整在上线前有可解释的质量证据。

### Phase 5：用户可见的主动陪伴与连接体验

**目标：** 在 Phase 2-4 的后端一致性、可观测性和质量门槛通过后，再扩展主动问候、
回顾入口和连接触达，确保新功能有可靠的触发、审计和关闭能力。

- [ ] 用聊天、日记、广场和通知记录聚合最近活动，而不是只依赖 `mid-memory` 更新时间。
- [ ] 将主动触发拆分为回顾、情绪陪伴、重要节点、匹配提醒等明确类型。
- [ ] 每次主动消息记录触发原因、使用的认知范围、关联事件和发送结果。
- [ ] 支持全局关闭、类型关闭、频率设置、静默时间和单条忽略。
- [ ] 对主动消息做去重、冷却、失败重试和幂等控制。
- [ ] 优先生成可执行的入口，例如“回顾这段经历”“继续昨天的话题”，减少泛化问候。
- [ ] 在连接互动阶段补充经过评测的定时触达和反馈时机，不把触达当作连接质量的唯一指标。

**验收标准：**

- 主动问候不会因为用户刚刚写日记或聊天而误判为长期不活跃。
- 用户能知道 Agent 为什么此时联系自己，并能关闭类似触发。
- 主动消息可以被评估为打开、回复、忽略或关闭，而不是只有发送记录。
- 主动行为和连接触达都能追溯到事件、认知范围、策略版本和发送结果。

### Phase 6：按需求扩展 Agent 能力

**目标：** 只有当真实任务证明需要时，才扩展平台能力。

- [ ] 为复杂记忆整理或匹配准备流程试点 Supervisor + 专业能力。
- [ ] 评估语音对话，优先考虑日记和低门槛表达场景。
- [ ] 评估外部知识接入和个人数据连接器。
- [ ] 评估多应用 API Key、配额和 MCP 工具生态。
- [ ] 在评测体系稳定、有足够高质量数据后，再评估微调或专用模型。

## 情景室边界

情景室继续作为独立的小游戏和探索性体验，不纳入日记、聊天、广场的自动认知摄取链路。

```text
情景室
  -> 参与情景
  -> 生成情景报告
  -> 用户主动选择是否带入一次对话或一次匹配
```

保留以下弱连接：

- 匹配后由 `ConnectionGuideService` 推荐适合双方的已审核情景。
- 用户主动点击“带入当前对话”或“用于本次匹配”时，才创建一次性上下文。
- 一次性上下文只传递必要的主题、诉求或状态标签，并设置有效期。
- 情景室继续使用独立的完成率、复玩率和满意度指标。

不做以下连接：

- 不自动把情景原文写入长期记忆。
- 不自动改变 `user-persona` 或 `MatchProfile`。
- 不因为用户玩过某个情景，就改变所有后续推荐。

## 关键风险与约束

- 记忆越强，隐私风险越高；任何长期记忆都必须有来源、范围和删除路径。
- 主动性越强，越容易产生打扰；默认低频，所有主动能力可关闭。
- 匹配互动越多不等于质量越高，必须加入双向反馈和安全信号。
- 多 Agent 会增加状态、成本、延迟和调试复杂度，必须由实际任务驱动。
- MCP 是开放能力边界，不应反过来成为核心业务数据的所有者。
- 训练不是当前第一优先级；先保证数据脱敏、评测可复现和质量回归。

## 最终成功标准

计划完成后，Yusi 应该能够做到：

1. 用户清楚 Agent 记住了什么，并能管理这些记忆。
2. 数据不足时，系统保持克制，不伪造稳定画像或强行制造互动。
3. Agent 的回复、洞察、报告和匹配都能使用合适的认知范围。
4. 匹配从推荐延伸到互动、反馈和连接结果。
5. 主动陪伴有明确理由、低频率和完整的关闭控制。
6. 重要 Agent 运行可以追踪，模型和 Prompt 变化可以评测。
7. 情景室仍然是独立、轻量、可探索的小游戏，不破坏主流程。
